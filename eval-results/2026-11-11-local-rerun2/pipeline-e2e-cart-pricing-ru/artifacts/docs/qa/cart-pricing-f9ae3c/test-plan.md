## Допущения

**Из отчёта Этапа 1, на которых построен тест-дизайн:**
- A2 — для пустой корзины проверяется только `subtotal = 0`; `shipping`/`total` не утверждаются.
- A3 — пороги считаются от суммы до скидки (TC-UNIT-005, TC-API-004).
- A4 — пороги 3000 и 5000 включительные (TC-UNIT-006, TC-UNIT-008, TC-E2E-003). Текущий `shipping_cost` использует `> 5000` — вероятный дефект продукта.
- A5 — округление скидки half-up (TC-UNIT-011).
- A6 — при участнике и распродаже скидка 0 (TC-UNIT-010, TC-API-003).
- A7 — `quantity` целое, граница 1..20 (TC-UNIT-001, TC-E2E-001).
- A8 — `price` ≥ 0, не более двух знаков (тестовые данные всех кейсов).
- A9 — N = 5000.00 − сумма до скидки, строка скрыта при сумме ≥ 5000 (TC-E2E-002/003).
- A1 (язык) — принято.

Допущения Этапа 1 не оспариваются. A2 оператором не подтверждено (оператор недоступен) — риск: при ответе на Q2 кейсы для пустой корзины будут добавлены.

**Собственные допущения Этапа 2:**
- **A10 (Этап 2)** — Формат N в строке доставки (Q3): допускаются разделитель тысяч (пробел или неразрывный пробел) и «,00»/«.00»; кейс TC-E2E-002 проверяет шаблон, а не точную строку.
- **A11 (Этап 2)** — Успешный ответ API — HTTP `200` с телом, содержащим ровно `subtotal`, `discount`, `shipping`, `total`. Статус успеха в ТЗ не назван; иные успешные коды сочтут расхождением.
- **A12 (Этап 2)** — Суммы в ответе API сравниваются как десятичные числа, независимо от типа «число/строка» и числа знаков (Q9 не решён).
- **A13 (Этап 2)** — API- и E2E-кейсы не автоматизируются в этом репозитории (нет API и UI). Этап 3 не должен придумывать сервер или страницу; такие кейсы получают статус `not run` с причиной.
- **A14 (Этап 2)** — Формула итога (REQ-14) вычисляется вне `pricing.py` (в модуле нет функции итога), поэтому проверяется на уровне API; unit-кейс, повторяющий формулу в тесте, не создаётся.
- **A15 (Этап 2)** — Отсутствие кейсов на quantity вне 1..20 на уровне API — осознанное: ожидаемый результат зависит от Q1/Q6.
- **A16 (Этап 2)** — Шкала риска: балл = влияние × вероятность; ≥ 15 красная зона P0, 10–14 оранжевая P1, 5–9 жёлтая P2, ≤ 4 зелёная P3. Вероятность дефекта повышена там, где есть известное расхождение с кодом (порог 5000).

## Распределение по пирамиде

| Уровень | Кейсов | Доля автоматизируемых |
|---|---|---|
| Unit | 11 | 61% |
| API | 4 | 22% |
| E2E | 3 | 17% |

Всего 20 кейсов; автоматизируемых по уровню — 18; из них 11 unit / 4 API / 3 E2E. Доля E2E 17% — в пределах бюджета 20%. Основная логика ТЗ (пороги, скидки, округление, граница количества) — чистые функции, поэтому лежит на unit. API-кейсы проверяют только связку расчёта с контрактом (флаги доходят, итог собирается, порог берётся от суммы до скидки) — по одному представителю на правило, без повторения unit-границ. E2E — три кейса, которые доказываются только на странице: количество не меняется после ошибки и показ/скрытие строки доставки. Негативных API-кейсов нет (Q1), безопасность не проектируется (Q5). Честно по репозиторию: выполнить здесь можно только 11 unit-кейсов; 7 API/E2E-кейсов ждут стенда. TC-UNIT-003 дублирует существующий тест, TC-UNIT-002 расширяет существующий (одна строка уже покрыта).

## Критерии входа и выхода

**Вход:**
- Код `src/shop/pricing.py` собирается, существующие тесты `tests/` проходят.
- Для API/E2E-кейсов: стенд с `POST /api/cart/price` и страницей корзины и тестовыми данными из кейсов (в этом репозитории не выполняется).

**Выход:**
- Все unit-кейсы P0/P1 выполнены; падения разобраны как дефект продукта или дефект теста. Ожидаемое падение TC-UNIT-006 (порог `>` против «от 5000») фиксируется как предполагаемый дефект и остаётся красным.
- Ни одного открытого дефекта P0/P1 без решения человека.
- В матрице нет строк без статуса; каждая заблокированная строка ссылается на существующий Q.
- Нет открытого блокирующего замечания Этапа 4.
- API/E2E-кейсы либо выполнены на стенде, либо явно отмечены `not run` в `autotest-summary.md` с причиной.
