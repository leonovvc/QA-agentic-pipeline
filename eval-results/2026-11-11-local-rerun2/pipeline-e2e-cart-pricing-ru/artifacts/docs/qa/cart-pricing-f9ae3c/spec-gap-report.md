# Spec Gap Analysis — Расчёт стоимости корзины (v1.2)

## Источник
Локальный файл `specs/cart-pricing.md`, версия 1.2 (снимок — `spec-source.md`). Текстовый документ, не PDF — уверенность извлечения полная. Справочно: в репозитории есть `src/shop/pricing.py` (только расчёт, без API/UI); он НЕ является источником требований, ТЗ главнее.

## Оценка тестируемости: 3
Арифметические правила (§1–§5) конкретны и проверяемы с граничными значениями, но API-контракт (ошибки, форматы, «быстро»), пустая корзина и источник N для UI не определены.

## Блокирующие пробелы
1. **Q1** — §6, последнее предложение: «Некорректный запрос возвращает ошибку с понятным сообщением». Не заданы HTTP-код, структура тела ошибки, перечень того, что считается некорректным, и тексты сообщений. Без этого нельзя спроектировать ни один негативный API-кейс с проверяемым ожидаемым результатом (REQ-18). [Q1]

## Противоречия
1. **Q2** — §2 «Пустая корзина имеет сумму 0 ₽» и §3/§5: доставка 300 ₽ действует при сумме < 5000, итог = сумма − скидка + доставка. Для пустой корзины формула даёт итог 300 ₽, что расходится с интуитивным «0 ₽» и неясно, должен ли API возвращать shipping 300 или 0. [Q2]
2. **Q3** — Контекст («фронтенд ничего не пересчитывает сам») против §7 (UI показывает «осталось N ₽») и §6 (API возвращает только `subtotal`, `discount`, `shipping`, `total`, без остатка до порога). Неясно, кто считает N. [Q3]

## Открытые вопросы
### Track A — для оператора, сейчас
Нет. Оператор недоступен; все решения оператора зафиксированы как допущения (A1–A9). Подтвердить: допустимо ли идти дальше на этих допущениях (в частности A2).

### Track B — для аналитика / владельца ТЗ
(по убыванию риска: деньги, доступ)
1. **Q5** — Эндпоинт `POST /api/cart/price` принимает `price`, `is_member` и `is_sale_period` от клиента. Кто источник истины для цены товара и для статуса участника/распродажи, проверяет ли сервер эти значения, требуется ли аутентификация и есть ли ограничение частоты запросов? (Владелец: продукт/бэкенд-лид.)
2. **Q2** — Какой результат должен возвращать расчёт для пустой корзины: `shipping` = 0 или 300 ₽, `total` = 0 или 300 ₽? И как именно «оформление недоступно» проявляется (неактивная кнопка, ошибка API, какой код)? (Продукт.)
3. **Q9** — Каким режимом округляется скидка 5% до копеек (half-up, банковское и т.д.) и в каком формате возвращаются суммы в ответе API (число или строка, всегда два знака после запятой)? (Бэкенд-лид.)
4. **Q1** — Какой HTTP-код, структуру тела ошибки и текст сообщения должен возвращать `POST /api/cart/price` для каждого вида некорректного запроса (пустое/отсутствующее поле, неверный тип, отрицательная цена, quantity вне 1..20, неизвестный флаг)? (Бэкенд-лид.)
5. **Q7** — Какие значения `price` допустимы (ноль, отрицательные, более двух знаков после запятой, верхняя граница), допускаются ли дубликаты `sku` в строках запроса, какое максимальное число строк? (Продукт/бэкенд.)
6. **Q6** — Что должно происходить, когда quantity вне 1..20 (а также 0, отрицательное, нецелое): какой текст ошибки видит покупатель, где он показывается, и какую ошибку возвращает API? (Продукт/дизайн.)
7. **Q3** — Как определяется N в строке «До бесплатной доставки осталось N ₽» (5000 − сумма корзины до скидки?), кто его считает — сервер (в каком поле ответа) или фронтенд, и в каком формате (копейки, округление)? (Продукт.)
8. **Q8** — Как выглядит блок доставки, когда сумма ровно 5000 ₽ и когда корзина пуста (строка скрыта, или «осталось 5000 ₽»)? (Продукт/дизайн.)
9. **Q4** — Какой измеримый критерий «быстро» для ответа API (например, p95 ≤ X мс при корзине до Y строк)? (Продукт/бэкенд.)
10. **Q10** — Входят ли в область ТЗ нефункциональные требования, не упомянутые явно: формат валюты и локализация, доступность строки о доставке, поведение при одновременном изменении корзины? (Продукт.)

## Допущения
1. **A1** — Язык вывода артефактов: русский (указан оператором). Оператор недоступен, Track A-вопросы не задавались.
2. **A2** — (к Q2) Для пустой корзины тесты проверяют только `subtotal` = 0 ₽ и недоступность оформления; значения `shipping`/`total` для пустой корзины не утверждаются до ответа на Q2. Разумно: только §2 явно задаёт для неё значение.
3. **A3** — (к §2, §3, §4) «Сумма корзины» — сумма до скидки; пороги 3000 и 5000 считаются от неё, а не от суммы после скидки. Основание: §2 определяет термин, §3/§4 используют его без уточнений.
4. **A4** — Пороги включительные: сумма ровно 5000,00 → доставка 0; ровно 3000,00 → скидка применяется («от», «не меньше»). Источник истины — ТЗ. Наблюдение для следующих стадий: `src/shop/pricing.py::shipping_cost` использует `> 5000` (строгое), что расходится с ТЗ («от 5000»); это возможный дефект продукта, а не повод менять допущение.
5. **A5** — Округление скидки: half-up до 0.01 (в ТЗ режим не указан; совпадает с распространённой практикой и текущей реализацией).
6. **A6** — Если одновременно `is_member` = true и `is_sale_period` = true, скидка = 0 (распродажа приоритетнее).
7. **A7** — `quantity` — целое число; граница 1..20 включительно (REQ-3).
8. **A8** — `price` — неотрицательное число с не более чем двумя знаками; поведение вне этого не проверяется до Q7.
9. **A9** — Строка «До бесплатной доставки осталось N ₽» использует N = 5000,00 − subtotal (до скидки) и скрыта при subtotal ≥ 5000; для пустой корзины не утверждается до Q3/Q8.

## Безопасность
Триггеры есть: пользовательский ввод, деньги, статус участника (привилегия), публичный API.
- Broken access control / аутентификация эндпоинта → **Q5** (не задано, кто может вызывать).
- Доверие к клиентским данным (price, is_member, is_sale_period — манипуляция ценой и скидкой) → **Q5**.
- Валидация ввода (типы, диапазоны, отрицательные/огромные значения, количество строк) → **Q1**, **Q7**.
- Rate limiting / ресурсоёмкость (большие корзины) → **Q5**, **Q4**.
- Утечка информации в сообщениях об ошибках → **Q1**.
- Не применимо: загрузка файлов, URL/вебхуки, мультитенантность, персональные данные (в ТЗ не фигурируют), административные действия.
