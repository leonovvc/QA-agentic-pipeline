# ТЗ: Расчёт стоимости корзины интернет-магазина — annotated

> Source: файл `specs/cart-pricing.md` (версия 1.2). Маркеры ниже соответствуют находкам в `spec-gap-report.md` по ID.

Версия 1.2 · Владелец: продуктовая команда «Корзина и оформление»

## Контекст

Покупатель видит в корзине итоговую сумму к оплате до перехода к оформлению заказа.
Расчёт выполняется модулем ценообразования `shop.pricing` на сервере; фронтенд получает
готовые суммы через API и ничего не пересчитывает сам. [Q5: TRACK B — при этом цена, `is_member` и `is_sale_period` приходят от клиента (п.6); доверяет ли сервер этим значениям?] Все суммы — в рублях с копейками. [Q11: TRACK B — тип/формат сумм в API (число или строка, знаков после запятой) не задан]

## Требования

1. **Количество.** Количество одного товара в строке корзины — от 1 до 20 включительно.
   Если покупатель пытается установить значение вне диапазона, показывается ошибка,
   а количество в строке не меняется. [Q7: TRACK B — текст и место показа ошибки не заданы; поведение API при выходе за диапазон не задано] [A4: ASSUMPTION — лимит применяется к каждой строке отдельно, дубли `sku` — отдельные строки; см. Q8]
   [Q8: TRACK B — допустимы ли несколько строк с одним `sku` (20 + 20), есть ли лимит строк/суммы]
2. **Сумма корзины.** Сумма корзины — это сумма «цена × количество» по всем строкам.
   Пустая корзина имеет сумму 0 ₽, оформление заказа для неё недоступно. [Q2: TRACK B — ПРОТИВОРЕЧИЕ с п.5: формула итога для пустой корзины даёт 300 ₽ (0 − 0 + 300), а здесь сумма 0; что возвращает API?] [A3: ASSUMPTION — для пустой корзины утверждаем только subtotal = 0; shipping/total зависят от Q2] [Q7: TRACK B — где блокируется оформление: только UI или также сервер?]
3. **Доставка.** Доставка стоит 300 ₽. При сумме корзины от 5000 ₽ доставка бесплатная. [Q10: TRACK B — «сумма корзины» до или после скидки участника?] [A2: ASSUMPTION — порог сравнивается с subtotal до скидки]
4. **Скидка участника.** Участники программы лояльности получают скидку 5% от суммы
   корзины, если сумма не меньше 3000 ₽. В период распродажи скидка участника
   не действует. [A8: ASSUMPTION — распродажа отключает только скидку участника, на доставку не влияет] Скидка округляется до копеек. [Q3: TRACK B — способ округления не задан (3000.10 × 5% = 150.005)] [A1: ASSUMPTION — округление half-up до 0.01] [A2: ASSUMPTION — порог 3000 сравнивается с subtotal до скидки; см. Q10]
5. **Итог.** Итог к оплате = сумма корзины − скидка участника + доставка. [Q2: см. противоречие с п.2 для пустой корзины]
6. **API.** `POST /api/cart/price` принимает строки корзины (`sku`, `price`, `quantity`)
   и флаги `is_member`, `is_sale_period`; возвращает `subtotal`, `discount`, `shipping`,
   `total`. [Q11: TRACK B — типы, форматы и ограничения полей (price 0/отрицательная/более 2 знаков, sku) не заданы] [A5: ASSUMPTION — quantity целое, price > 0 с ≤ 2 знаками, суммы с двумя знаками] [A7: ASSUMPTION — значения price и флагов принимаются как есть; защита от подмены не утверждается, см. Q5] [Q6: TRACK B — аутентификация, лимиты частоты, максимум строк и размера тела не заданы] Ответ должен приходить быстро. [Q4: TRACK B — нет измеримого критерия «быстро»] Некорректный запрос возвращает ошибку
   с понятным сообщением. [Q1: BLOCKING — не определено, что такое некорректный запрос, какой статус, формат тела и текст сообщения; негативные API-кейсы невозможно записать]
7. **Отображение.** На странице корзины рядом с итогом показывается строка
   «До бесплатной доставки осталось N ₽», пока порог не достигнут. [Q9: TRACK B — как считается N (до/после скидки), формат N, показывается ли для пустой корзины] [A6: ASSUMPTION — N = 5000.00 − subtotal, два знака, строка видна при subtotal < 5000.00] [Q12: TRACK B — нефункциональные требования (a11y, локализация, браузеры) не заданы; отсутствие = пробел, не исключение]
