## Оценка тестируемости: 3

## Блокирующие пробелы

1. **Q1** — п.6, последнее предложение: «Некорректный запрос возвращает ошибку с понятным сообщением». Не определено, что считается некорректным запросом (пустой список строк, отсутствие полей, неверные типы, отрицательные/нулевые цены, количество вне 1..20 на уровне API), какой HTTP-статус, какой формат тела и какое сообщение. Без этого невозможно записать наблюдаемый ожидаемый результат ни для одного негативного API-кейса. Маркер [Q1] в `spec-annotated.md`. Кейсы по REQ-16 блокируются до ответа.

## Противоречия

1. **Q2** — п.2 vs п.5: п.2 «Пустая корзина имеет сумму 0 ₽», а формула п.5 для пустой корзины даёт итог 0 − 0 + 300 = 300 ₽ (доставка п.3 не освобождена для сумм < 5000). Неясно, должен ли API при пустой корзине возвращать `shipping = 300` и `total = 300` или 0. Не блокирует (покрыт допущением A3), но влияет на ожидаемый результат граничного кейса «пустая корзина».

## Открытые вопросы

### Track A — для вас, сейчас
Нет. Оператор недоступен; вопросы, которые обычно задаются оператору (допустим ли частичный ТЗ-черновик, какое из двух допущений принять), решены допущениями A1–A8 ниже.

### Track B — для аналитика / владельца ТЗ
Порядок — по риску блокируемого требования (деньги и доступ — первыми). Каждый вопрос самодостаточен.

1. **Q5** — (владелец: продукт + бэкенд-лид) В `POST /api/cart/price` цена (`price`) каждой строки и флаги `is_member` и `is_sale_period` приходят от клиента. Должен ли сервер доверять этим значениям или брать цену по `sku` из каталога, статус участника — из сессии/профиля пользователя, а период распродажи — из серверной конфигурации/времени? Что должен возвращать сервер, если присланная цена не совпадает с каталожной или клиент заявляет `is_member=true` для не-участника?
2. **Q3** — (владелец: продукт / финансы) Каким способом округляется скидка участника до копеек (математическое «половина вверх», банковское, отбрасывание, округление вверх)? Пример: сумма корзины 3000.10 ₽ × 5% = 150.005 ₽ — это 150.01 или 150.00? Округляется ли только скидка, или также промежуточные суммы?
3. **Q10** — (владелец: продукт) Пороги 3000 ₽ (скидка участника) и 5000 ₽ (бесплатная доставка) сравниваются с суммой корзины до вычета скидки или с суммой после скидки? Пример: участник, сумма корзины 5000.00 ₽, скидка 250.00 ₽ — доставка бесплатная (по 5000 до скидки) или платная (4750 после скидки)?
4. **Q2** — (владелец: продукт) Какие `subtotal`, `discount`, `shipping`, `total` должен возвращать API для пустой корзины (пустой массив строк): 0/0/0/0 или 0/0/300/300? Является ли пустой массив строк корректным запросом либо ошибкой?
5. **Q1** — (владелец: бэкенд-лид / аналитик) Какие запросы к `POST /api/cart/price` считаются некорректными и что именно возвращается: HTTP-статус, формат тела ошибки, код и текст сообщения? Перечислите случаи: нет обязательного поля, неверный тип, `quantity` вне 1..20 или нецелое, `price` отрицательная/нулевая/с более чем двумя знаками, пустой список строк, неизвестные поля.
6. **Q6** — (владелец: бэкенд-лид / безопасность) Требует ли `POST /api/cart/price` аутентификации? Есть ли ограничения частоты запросов, максимальное число строк в запросе и максимальный размер тела? Что возвращается при превышении?
7. **Q7** — (владелец: продукт / дизайн) Где и как показывается ошибка при попытке выйти за диапазон количества 1..20 (текст сообщения, место на странице), и что происходит при такой попытке на уровне API (ошибка или обрезка до границы)? Где блокируется оформление заказа пустой корзины: только кнопка в UI или также сервер оформления отклоняет запрос?
8. **Q8** — (владелец: продукт) Лимит 1..20 действует на строку. Если один и тот же `sku` присутствует в нескольких строках (например, 20 + 20), это допустимо? Есть ли ограничения на число строк в корзине и на максимальную сумму?
9. **Q9** — (владелец: продукт / дизайн) Как вычисляется N в строке «До бесплатной доставки осталось N ₽»: 5000 − сумма корзины до скидки или после скидки? В каком формате показывается N (копейки, разделитель)? Показывается ли строка для пустой корзины? Исчезает ли строка ровно при сумме 5000.00 ₽?
10. **Q11** — (владелец: бэкенд-лид) Какие типы и форматы у полей API: `price` и суммы в ответе — число или строка, сколько знаков после запятой, допустима ли цена 0, максимальное значение цены; `quantity` — только целое; `sku` — формат и допустимая длина?
11. **Q4** — (владелец: продукт / бэкенд-лид) Какой измеримый критерий у «Ответ должен приходить быстро»: например p95 ≤ X мс при N запросах в секунду для корзины из M строк?
12. **Q12** — (владелец: продукт) Какие нефункциональные требования применимы к строке и странице корзины: доступность (a11y), локализация формата рубля, поддерживаемые браузеры/устройства? Спецификация молчит.

## Допущения

1. **A1** — Q3, п.4: округление скидки — математическое «половина вверх» до 0.01 ₽ (коммерческое округление); принято как наиболее распространённое по умолчанию для денежных сумм. Кейсы с половинными значениями помечаются зависимыми от Q3.
2. **A2** — Q10, п.3 и п.4: оба порога сравниваются с суммой корзины (`subtotal`) до вычета скидки; это буквальное прочтение «при сумме корзины» и совпадает с определением «сумма корзины» в п.2. Например: участник, subtotal 5000.00 → discount 250.00, shipping 0.00, total 4750.00.
3. **A3** — Q2, п.2/п.5: для пустой корзины сумма = 0 ₽, оформление недоступно; ожидаемые `shipping`/`total` в API для пустой корзины в кейсах не утверждаются сверх `subtotal = 0` (формула даёт 300 ₽, п.2 говорит о сумме 0) — кейс помечается зависимым от Q2.
4. **A4** — Q8, п.1: каждая строка корзины проверяется независимо по диапазону 1..20; повторяющиеся `sku` в разных строках считаются отдельными строками (суммируются).
5. **A5** — Q11, п.6: `quantity` — целое число; `price` — положительное число не более чем с двумя знаками после запятой; суммы в ответе — числа с двумя знаками. Допущение используется только для позитивных кейсов; негативные границы цены не утверждаются (см. Q1).
6. **A6** — Q9, п.7: N = 5000.00 − subtotal (до скидки), в рублях с двумя знаками; строка видна, пока subtotal < 5000.00; в пустой корзине не проверяется.
7. **A7** — Q5, п.6: для функциональных кейсов значения `price`, `is_member`, `is_sale_period` принимаются сервером как есть (в рамках контракта п.6); проверка защиты от подмены не утверждается до ответа на Q5.
8. **A8** — п.4: период распродажи отключает только скидку участника; на доставку и пороги он не влияет (спецификация не связывает его ни с чем другим).

## Безопасность

Триггеры в ТЗ есть: деньги (расчёт итога), пользовательский ввод (API), статус участника программы лояльности (привилегия). Применимые строки OWASP:

| Строка | Применима | Результат |
|---|---|---|
| Broken Access Control / доверие к клиентским данным (A01) | да | Q5: цена, `is_member`, `is_sale_period` приходят от клиента — риск подмены цены и самовыдачи скидки; Q6: нужна ли аутентификация |
| Injection / валидация ввода (A03) | да | Q1, Q11: допустимые типы и форматы `sku`, `price`, `quantity` не заданы; переполнение/некорректные числа |
| Insecure Design / бизнес-логика (A04) | да | Q5, Q8: подмена цены, дубли `sku` обходят лимит 20 на товар; Q6: ограничения числа строк и частоты |
| Security Misconfiguration / утечка в сообщениях об ошибках (A05) | да | Q1: формат и содержание сообщения об ошибке не определены (риск утечки внутренних деталей) |
| Rate limiting / DoS | да | Q6: нет лимитов на размер запроса и частоту |
| Персональные данные | частично | Сам запрос ПДн не содержит; статус участника — персональный атрибут, источник не задан (Q5) |
| Загрузки файлов, URL/webhooks, мультиарендность, административные действия | нет | В ТЗ нет соответствующих функций |
