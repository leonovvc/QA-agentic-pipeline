## Объём

**В объёме (тестируется):** REQ-1, 3, 4, 5, 7, 8, 9, 10, 11 (при допущении A1), 12, 13, 14, 17, 18, 19.

**Вне объёма:** промокоды, подарочные сертификаты, налоги (ТЗ «Вне рамок»). Нефункциональные требования (a11y, браузеры — Q12) не планируются, пока спецификация молчит.

**Заблокировано:**
- REQ-2 (текст и место показа ошибки) — Q7.
- REQ-6 (где блокируется оформление пустой корзины) — Q7.
- REQ-15 («быстро») — Q4, измеримого критерия нет; нагрузочные кейсы не пишутся.
- REQ-16 (ошибка для некорректного запроса) — Q1 (Блокирующий пробел): статус, формат и текст ошибки не заданы, ожидаемый результат не выдумываем. Негативные API-кейсы не пишутся.
- Кейсы безопасности по Q5 (доверие к клиентским цене/флагам) и Q6 (аутентификация, лимиты) не проектируются: ТЗ не задаёт безопасное поведение. Вместо них — исследовательский чартер TC-MAN-004.
- Значения `shipping`/`total` для пустой корзины — Q2 (не утверждаются).

## Допущения

**Унаследованы от Stage 1 (тест-дизайн строится на них):**
- A1 — округление «половина вверх» (TC-UNIT-013).
- A2 — пороги сравниваются с суммой до скидки (TC-API-003, TC-UNIT-007/008/009/010).
- A3 — для пустой корзины утверждается только `subtotal = 0.00` (TC-UNIT-005).
- A4 — дубли `sku` суммируются как отдельные строки (TC-UNIT-004).
- A5 — типы полей для позитивных кейсов (TC-API-001).
- A6 — N = 5000.00 − сумма до скидки (TC-MAN-002).
- A8 — распродажа отключает только скидку (TC-UNIT-012, TC-API-004).
- A7 унаследовано, но не используется: кейсов на подмену цены нет.

**Собственные допущения Stage 2:**
- **A9 (Stage 2)** — Имя поля со строками в теле запроса API — `lines` (ТЗ его не называет). Действует, пока Q11 не решён.
- **A10 (Stage 2)** — Отсутствующий в `pricing.py` расчёт итога и HTTP-эндпоинт будут добавлены; до этого API-кейсы получают статус `not run`. Кейсы не подменяются тестом, который сам считает формулу.
- **A11 (Stage 2)** — UI в репозитории нет, поэтому E2E-автотестов не планируется; UI-проверки ручные.
- **A12 (Stage 2)** — Шкала приоритетов по Score (Impact × Probability): 20–25 → P0, 12–19 → P1, 6–11 → P2, ≤5 → P3.
- **A13 (Stage 2)** — Оценка вероятности учитывает чтение кода: `shipping_cost` в `pricing.py` сравнивает `>` с порогом, а ТЗ говорит «от 5000» (включительно) — вероятность дефекта по REQ-8 оценена 4.

Обоснование. Вся арифметика (границы, скидка, порог, округление) живёт в чистых функциях `shop.pricing`, поэтому проверяется unit-тестами с `Decimal`: каждый прогон занимает миллисекунды, зависимостей нет — pytest и существующая фикстура `mug` в `tests/conftest.py`. API-уровень — только 4 кейса: контракт ответа и сборка итога (формулы итога в модуле нет), по одному представителю каждого правила, без повторения всех границ. E2E нет осознанно: в репозитории нет ни фронтенда, ни браузерного фреймворка, а добавление Playwright ради двух проверок отображения стоило бы слишком дорого по сравнению с их риском (REQ-17, REQ-19 — P1/P2); они вынесены в ручные. Бюджет E2E (20%) не превышен. API-кейсы требуют эндпоинта, которого пока нет (A10) — это единственные кейсы с риском `not run`.

## Критерии входа и выхода

**Вход:** `pytest` запускается в репозитории (`pythonpath = src`); существующие тесты `tests/test_cart_lines.py` зелёные; для API-кейсов — развёрнут эндпоинт `POST /api/cart/price`.

**Выход:**
- Все кейсы P0 и P1 выполнены и пройдены, либо падение квалифицировано как дефект продукта с записью в `autotest-summary.md`. Ожидаемое падение: TC-UNIT-008 (порог `>` вместо `>=`).
- Нет открытых дефектов P0/P1 без решения.
- Каждый REQ в матрице — covered, out of scope или blocked с названным Q; строк GAP нет.
- Нет открытого блокирующего замечания в `qa-review-report.md`.
- Заблокированные REQ-2, 6, 15, 16 вернутся в план после ответов на Q7, Q4, Q1.
