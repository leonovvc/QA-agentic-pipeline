# Анализ пробелов ТЗ — Расчёт стоимости корзины интернет-магазина (v1.2)

## Источник
Файл `specs/cart-pricing.md` (слепок: `docs/qa/cart-pricing-f9ae3c/spec-source.md`). Текст, не PDF — уверенность извлечения полная. Владелец ТЗ: продуктовая команда «Корзина и оформление». Операторa в прогоне нет, Track A вопросов не задавалось (см. «Открытые вопросы»). Реализация `src/shop/pricing.py` прочитана только для сверки; отчёт — про ТЗ.

## Оценка тестируемости: 3
Денежные правила (количество, доставка, скидка, итог) сформулированы числами и проверяемы; снижают оценку неопределённая база порога бесплатной доставки, отсутствующий контракт ошибок API, «быстро» без цифр и неопределённое поведение пустой корзины в API.

## Блокирующие пробелы
1. **Q1** — п.6, предл.3 (REQ-13, REQ-16): нет контракта валидации и ошибок. Не заданы обязательность полей, типы, допустимые значения `price` (0, отрицательная, >2 знаков), `sku` (пусто), статус-код, формат тела ошибки; «понятное сообщение» непроверяемо. Без этого нельзя спроектировать ни один негативный API-кейс. [Q1]
2. **Q2** — п.3, предл.2 (REQ-8): неясно, «сумма корзины» для порога бесплатной доставки берётся до или после скидки участника. Для участника с суммой 5000–5263,15 ₽ итог различается на 300 ₽, т.е. ожидаемый результат граничных кейсов не выводится из ТЗ. [Q2]

## Противоречия
1. **Q8** — Контекст («сервер считает, фронтенд получает готовые суммы, ничего не пересчитывает») vs п.6 (API принимает от вызывающего `price` и флаги `is_member`, `is_sale_period`): цена и статус участника приходят из клиентского запроса, источник истины не определён. [Q8]
2. **Q11** — п.3, предл.2 («от 5000 ₽» = включительно) vs `src/shop/pricing.py::shipping_cost` (строго `> 5000`): при сумме ровно 5000 ТЗ даёт 0 ₽, код — 300 ₽. Это расхождение ТЗ и реализации, а не внутри ТЗ; зафиксировано для сверки. [Q11]

### Track B — для аналитика / владельца ТЗ

4. **Q9** — Требуется ли аутентификация для `POST /api/cart/price`, есть ли ограничение частоты запросов и максимальное число строк/размер тела запроса? Какой ответ при превышении? (Владелец: бэкенд-лид.)
5. **Q1** — Какие поля запроса обязательны, их типы и допустимые значения (`price` ≤ 0 или более 2 знаков после запятой, пустой/дублирующийся `sku`, нецелое `quantity`, отсутствующие флаги)? Какой статус-код и формат тела ошибки (код, текст, поле) возвращается для некорректного запроса? (Владелец: аналитик/бэкенд.)
6. **Q3** — Какие `shipping` и `total` возвращает API для пустой корзины: по формуле п.5 получается 300 ₽, при этом сумма корзины 0 ₽ и оформление недоступно. Должна ли доставка быть 0 ₽? Как именно «недоступно» оформление (кнопка неактивна, ошибка API)? (Владелец: продукт.)
7. **Q4** — Как проявляется отклонение количества вне 1…20: точный текст ошибки, где проверяется (только UI или и API), что возвращает API для `quantity` = 0, 21, отрицательного, нецелого? (Владелец: продукт/аналитик.)
8. **Q6** — Режим округления скидки «до копеек» (half-up / банковское / вниз)? Допускает ли `price` более 2 знаков? В каком типе возвращаются суммы в ответе (строка `"1234.50"` или число), и сколько знаков? (Владелец: бэкенд-лид.)
9. **Q7** — Как считается N в «До бесплатной доставки осталось N ₽»: 5000 − сумма до скидки или после; формат (копейки, разделители); что показывать при пустой корзине и при сумме ровно 5000 ₽? (Владелец: продукт/дизайн.)
10. **Q10** — Что делать при нескольких строках с одним `sku` в запросе и при товаре с ценой 0 ₽: допускается ли, суммируются ли количества, проверяется ли лимит 20 на строку или на суммарное количество по `sku`? (Владелец: продукт.)

## Допущения
1. **A1** — Q2: порог бесплатной доставки проверяется по сумме корзины до скидки (буквальное чтение «сумма корзины» = п.2). Временно, до ответа на Q2; граничные кейсы «участник у порога 5000» помечаются как зависящие от Q2.
2. **A2** — Q3: для пустой корзины API возвращает `subtotal` 0.00, `discount` 0.00, `shipping` 0.00, `total` 0.00 (нечего доставлять). Формула п.5 буквально дала бы 300 ₽; допущение — только для планирования, расчёт пустой корзины на уровне кейса помечается зависимым от Q3.
3. **A3** — п.4: порог 3000 ₽ для скидки проверяется по сумме корзины (до скидки), включительно (`>= 3000`); скидка = сумма × 0.05.
4. **A4** — Q6: округление скидки — half-up до 0.01.
5. **A5** — Q1: отсутствующие флаги `is_member`/`is_sale_period` трактуются как `false`; `quantity` — целое число.
6. **A6** — п.4+п.5: скидка вычитается из суммы до прибавления доставки; доставка скидкой не уменьшается.
7. **A7** — Q4: ограничение 1…20 действует и на API (`quantity` вне диапазона — ошибка), а не только в UI.
8. **A8** — Вне рамок (промокоды, сертификаты, налоги) исключены из тест-дизайна; п.7 (отображение) тестируется на уровне E2E при условии ответа на Q7.

## Безопасность
Триггеры: пользовательский ввод (тело API), деньги (цена, скидка), доступ-зависимая логика (статус участника), публичный эндпоинт.
- **Broken Access Control / доверие клиенту (A01, A04):** `price`, `is_member`, `is_sale_period` приходят из запроса → Q8 (подмена цены/статуса).
- **Аутентификация, ограничение частоты, размеры (A04/A07):** в ТЗ ничего → Q9.
- **Валидация ввода / инъекции (A03):** контракт валидации `sku`, `price`, `quantity` отсутствует → Q1; поведение при дублях → Q10.
- **Бизнес-логика, злоупотребление (A04):** отрицательная цена/количество могут уменьшать итог → Q1, Q4.
- **Раскрытие информации через ошибки (A05):** формат сообщения об ошибке не определён → Q1.
- **Логирование/мониторинг:** не покрыто ТЗ; отдельного Q не заводилось, учитывается в Q9.
- Не применимо: персональные данные и загрузка файлов — в ТЗ отсутствуют; мультиарендность — не упомянута.
